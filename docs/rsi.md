# RSI：闭环、回归门、跨轮

RSI = 采集 → 归因 → 提案 → 验证 → 采纳/回滚。唯一写源文件的地方是最后一步。

```
采集 collectFailures  ←  一份 EvalReport
  ↓
归因 attribute         ←  规则式聚类（可单测、可解释、零成本）
  ↓
提案 propose           ←  唯一用 LLM 的一步：怎么改
  ↓
验证 verify            ←  在内存 AssetSet 副本上改，跑 eval，零副作用
  ↓
采纳 accept / 回滚 revert  ←  唯一写源文件的地方（原子写 + journal）
```

## 回归门：字典序 + 硬否决

不是一个加权总分：

| 条件                             | 结论                                 |
| -------------------------------- | ------------------------------------ |
| 两份报告的用例集不同             | 否决（`case_set_changed`，分母变了） |
| 有「基线过、候选挂」的用例       | 否决（能指名是哪条）                 |
| 同上，但那些用例历史上就在抖     | 放行，单独标 `case_regression_flaky` |
| 通过率下降（同名用例内）         | 否决                                 |
| 通过率下降，但重复采样下不显著   | 放行，单独标 `pass_rate_dropped_not_significant` |
| 通过率没升、成本/ token 涨超 10% | 否决                                 |
| 通过率提升                       | 放行（token 涨多少都放行，只记录）   |

第 5 行只在 `--repeat n`（n ≥ 2）下有采样量支撑时才可能出现：两比例单侧 z 检验没过
临界值 `-1.645`，说明「这次下降」与「同一分布的两次抽样」分不开。放行不等于没记 ——
code 与理由都写进账本，理由里带次数、采样量、z 值。**采样不足时该做的是加大 `--repeat`，
不是再改一版提示词**；这也正是 RSI 里唯一一处「看见退步却放行」的分支，所以它必须
单独可见，不能混进 `pass`（详见 `docs/evals.md` 的「重复采样」一节）。

**「历史上就在抖」的用例不当判据。** 第 3 行（能指名到用例的否决）有一个前提：那条
用例**可信**。同一条用例、同一份资产，昨天过一个挂两次，今天的失败就可能只是一次坏运气 ——
拿它否决提案，等于让随机数决定闭环往哪走。所以历史账本里被标成抖动的用例（判定依据见
`docs/evals.md` 的「历史与抖动」）会从这里被摘出去，结论单独标 `case_regression_flaky`，
`ok: true`。**只要混着一条稳的用例变失败就照旧否决** —— 这两种错误的代价不对称：放过一次
真退步，它会进账本、成为下一轮的先验，错误就此复利；而错拒一次，损失只是这一轮白跑。

为什么不用加权总分：权重随手一调就能让任何结论成立。字典序的每一条都能用一句人话解释，而 RSI 最贵的成本不是算力，是**人重新信任一套自己看不懂的提示词**。

第 5 行的宽容是**单向**的：通过率涨了就放行、成本涨多少只记录。这个宽容成立（用预算换能力是合理交易），但它需要一只配套的刹车，见下面的「净简化配额」——**改的是调度，不是判据**。

## 「可比」需要证据，不是默认成立

报告会带上 `model` + `models`（实际用过哪些）/ `harnessVersion` / `finishedAt` / `caseFingerprint`；`harness report` 把它们打出来，不一致时告警。

`model` 是生效值（单值），`models` 是**实际尝试过的集合** —— 配了 fallback 链之后两者在降级发生时就分叉，而「能不能比」要读的是后者：基线降级过、候选没降级，通过率差异会被读成 agent 的进退步。

用例集变了默认拒绝（加一条候选没做的用例会让分母变大、通过率下降，那不是「整体退步」，是基线过期）；确实只想比同名用例时加 `--allow-case-set-change`，此时 token 与成本也只在同一批用例上算，结论里写明「只比对 N 条」。

判「更贵」优先用**美元成本**（`trace.totalUsage.costEstimate` 逐条累加），两边都有读数时不再看 token —— token 只对同一模型可比，而「换模型」是合法提案。任一条用例没有成本读数（模型不在价格表内）就退回 token，并把 `costBasis` 一并记录：结论用的是哪个指标，必须可复核。「不知道花了多少」与「花了 0」是两件事，混成一个数会让成本门静默失效。

## 一轮最多采纳一个

同时采纳三个，评测从 70% 涨到 85%，没人知道是哪个起的作用 —— 单变量是让「采纳记录」变成可信知识的唯一做法。

## 一轮会试几个目标

「改谁」由数据决定，但**不是只定一次**。候选是一张有序表（`src/rsi/targets.ts`）：

1. **失败用例实际走过的技能与子 agent**，按覆盖用例数降序；
2. **主 agent**（回答这些用例的那个），永远排最后。

主 agent 排最后是刻意的：它几乎覆盖**全部**失败用例（它就是答的那一个），按数量排它必然
第一 —— 那样每一条提案都会去改最宽的那份提示词，「影响面小优先」这条设计就名存实亡了。

主 agent 是**谁**也按证据取，不是 `assets.agents[0]`：`--agent` > `FailureSample.routedTo`
的多数派 > 第一个 agent。多 agent 工程里用「第一个」会改到另一个 agent 的提示词上，
白烧一轮验证而报告里完全看不出异常。

**首选被否就换下一个**（`src/rsi/alternate.ts`）。真机上最常见的死法：

```
归因指向一个技能 → 改技能 → 回归门否决（另一条用例挂了）→ 整轮结束
而病根在 agent 的提示词上，它从头到尾没被考虑过
```

现在会换一个候选资产再提一次案，然后走**同一套判定**（预算闸、回归门、变好判据）。四条边界：

- **每轮最多一次**。这是「被否之后的第二次机会」，不是「一直试到成功」—— 后者会把一轮的
  成本摊成无底洞，单变量原则也不再成立；
- **不占 `--max-verify` 配额**。那个上限管「一次提案能验几条」，与重试不是同一个概念，
  混在一起会让 `--max-verify 1` 把重试一起关掉；
- **简化轮不做**。那一轮只接受净简化，换目标等于换个地方变胖；
- **`proposals` 为空时不做**。模型自己说「改不出来」时，排除列表是空的，再问一遍它会选
  同一个目标、给出同一个答案 —— 花一次调用买一个已知结果。

换过目标的那一轮会在 cycle JSON 里留 `alternate`（`modeId` / `avoided` / `target`），
CLI 也会打一行「首选目标被否，换目标再试一次」。不落这个字段，「这轮为什么有两条提案」
在记录里就只能靠猜。

**超长会再问一次**（`src/rsi/propose-prompt.ts` 的 `tightenPrompt`）。上限（`max(原文×3, 400)`）
一个字没放宽 —— 放宽比误杀危险。但模型有时只差「把三段并成一段」，所以超限后会把
「你上一稿 N 字、上限 M 字」连同稿子一起发回去让它压一次，还超才丢弃。

**回归门会拿哪批用例比，提前告诉它**（`src/rsi/audience.ts`）。提案提示词里多一节：

```
## 这份正文现在还服务哪些用例
当前**通过**：draft-refund, triage-invoice
这些用例现在是对的。改写之后它们必须仍然通过 —— 回归门会逐条比较，
任何一条从通过变失败都会直接否决整条提案（哪怕目标用例确实修好了）。
```

这一节是被真机逼出来的：连续两轮，提案都改对了目标、修好了目标用例，却各自弄坏**另一条
原本通过**的用例（`triage-invoice` / `triage-outage`），被门逐条否决。模型看得到的只有
「失败的那一条」，它不知道这份正文同时服务着谁 —— 于是为修一条把另一条写坏，而那次评测
的钱已经花了。判据一个字没松（任何一条通过变失败仍然整条否决），只是把判据提前说清。

### 真机数据（2026-11-28，DeepSeek）

5 次尝试、2 次采纳，最终用例通过率 1/3 → 3/3：

| 场景 | 结果 |
|---|---|
| 有技能的工程，病根在 agent 的输出约定 | 归因指到技能 → 回归门 BLOCK → 换成主 agent 再提 |
| agent 正文 76 字 | 扩到 474 > 上限 400，压缩机会也用掉 → 丢弃 |
| agent 正文 302 字 | 扩到 1021 > 906，同上 |
| 同上 | PASS，+33.3pt → 采纳并写盘 |
| 同上 | 自动进入简化轮（成本涨 112% 触发），PASS，−75.7% → 采纳 |

余额 ¥2.62 → ¥2.40（约 $0.031，结算滞后；估算求和 $0.066 属上界）。

补上「还服务哪些用例」之后，同一条命令在同一个工程上第一次跑到采纳：

```
提出 2 个提案，验证 2 个：
  首选目标被否，换目标再试一次：skill:queue-policy → agent:triage
  BLOCK  p-…0 → skill:queue-policy：1 条原本通过的用例变失败：triage-invoice
  PASS   p-…1 → agent:triage：修好 1 条（triage-escalate），通过率 +20.0pt，成本 +13.1%
留出集第 1 批 1 条
采纳 1 个：p-…1
```

**别拿单次观测判回归**。同一次采纳三分钟后 `rsi regress` 报 `draft-refund` 回归，再跑一遍
就恢复 6/6 —— 那是采样噪声。所以 `rsi regress` 现在也读抖动账本（`flakyCases`）：已知抖动的
用例失败时标「（已知抖动）」、退出码不算失败、`--revert` **不会**回滚。与回归门
`case_regression_flaky` 同一口径 —— 把噪声当判决的代价，是回滚掉一条真修好东西的改动。

## 留出集：**每一批**只验一次

`split: holdout` 的用例只在候选选定后验一次 —— 这是一轮之内的事。跨轮时它不够：
留出集不变、轮次无限，30 轮 × 每轮 5% 显著性的累积假阳性约 **78%**。每一轮的门都在
"合法地"放过一点噪声，而每一轮都比上一轮更自信。

所以留出集要能被**消耗**：

```md
---
name: holdout-batch-2
split: holdout
phase: 2 # 批次号（正整数）。不写 = 整份留出集算同一批
expect_contains: 保留
---
```

| 规则                     | 行为                                                                          |
| ------------------------ | ----------------------------------------------------------------------------- |
| 声明了 `phase`           | 每轮挑**序号最小、还没用过**的那批；该批用掉就换下一批                        |
| 所有批都用过             | **拒绝**验证（不是退回第一批发重用），提示补一批新用例或收工                  |
| 没声明 `phase`（老工程） | 整份算一批，照旧可复用；但复用次数被记下来并在 `rsi status` 里出声            |
| 消耗与结果               | **无关**：通过也算用过、否决也算用过。只在"通过"时记账等于免费重抽，正是假阳性来源 |
| `--dry-run`              | **也消耗**：验一眼就是看一眼，资产没动不代表数据没被看过                      |
| 验证本身崩了             | **不消耗**：补丁过期、装配错不是一次观测；这条缝的代价是重试，收益是配置错不烧掉一整批 |

消耗账落在 `.workspace/rsi/holdout-uses.jsonl`（每行：批次、用例名、提案、通过与否），
轮次记录里同时写 `holdoutBatch`（`phase` / `cases` / `priorUses` / `enforced`）——
两处都在，才能回答"哪一批被哪一轮用掉了"。账本坏一行就报错，不跳过：少读一条消耗记录，
等于白送一批已经用过的留出集。

基线也要**跟着批次收窄**（`subsetReport`）：候选只跑这一批，拿整份留出集当基线会被门判成
`case_set_changed` —— 那不是判定标准变了，是两边比的不是同一批。

## 净简化配额：给成本棘轮装刹车

回归门第 5 行让"通过率提升时成本随便涨"，于是资产可以**每轮胖一点、永远不用瘦**。
RRSI 的对照组就是这么长成 3.80M tokens / 更低 OOD 的。

做法是**调度**而不是判据：连续 `every`（缺省 5）条改动没让资产变小，或累计成本增幅
超过 `maxGrowth`（缺省 50%，相对增幅逐条相加，不是复利），下一轮就是**简化轮**。

| 简化轮里发生什么     | 行为                                                                     |
| -------------------- | ------------------------------------------------------------------------ |
| 提案提示词           | 明确写"只许删与合并"，并给出**目标字数**（只说"请简化"，模型只会改措辞） |
| 变胖的提案           | 在**跑评测之前**就被挡下（省的是真金白银），理由带字数变化               |
| 验收判据             | 「通过率没变、但资产确实更小」算值得 —— 平时这条明确不算（会污染 git 历史） |
| 判定"更小"           | 正文净减少 ≥ `minReduction`（缺省 5%）。只删一个字就能满足的话，配额会变成一枚印章 |
| 一条简化被采纳       | 两个计数一起归零（配额兑现）                                             |
| 一轮交不出简化       | 不采纳、`--rounds` 以 `shrink_stalled` 停下并说清"这轮只许删"：人去删一段，或换一批用例 |

状态**不落游标**：每次从 `cycles/*.json` 的采纳记录与门读数现算（`shrink.ts`）。
多一个"当前是不是简化轮"的文件，就多一处会与历史不一致的真相。

配额的边界要说清：它只在**有失败样本**的轮次里生效（`runCycle` 没有失败就直接收工）。
这不是漏洞 —— 没有采纳就没有变胖，棘轮此时本来也没在转。全部用例都通过的工程想瘦身，
就手动删，然后下一轮基线自然变便宜。

## 三层可观测（借鉴 AHE / Superagentic 的思路）

| 层   | 产物                                                                                                                        | 回答的问题                                      |
| ---- | --------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| 经验 | `harness evidence --from-report <报告.json>` → `.workspace/evidence/<id>/` 的 `overview.md` / `detail/*.md` / `raw/*.jsonl` | 失败到底是什么样？（原始 trace 不整坨塞提示词） |
| 决策 | 提案与 journal 里的 `manifest`：依据、假设、预测、风险                                                                      | 当时**为什么**相信这个改动？                    |
| 对账 | `harness rsi ledger [--json]`                                                                                               | 预测兑现了吗？（被拒的尝试也进账本）            |

清单在提案时、验证之前写好，不许事后倒推；账本把 journal 的预测和 cycle 的实际门结果拼在一起，标 `realized` / `not_realized` / `unverified`。证据目录以 id 命名且**不覆盖**：它是事后审计物，覆盖等于销毁历史。

## 手写提案与自动提案走同一条门

自动闭环与手写提案走同一条路：`rsi accept --from` 也先按 train 验证，再跑留出集，最后才落盘。CLI 没有任何开关能跳过留出集；库层的 `acceptProposal` 也会拒绝「工程配了 holdout、却没有留出集验证结果」的调用（手伪造内部结果结构体属于越过信任边界）。

**提案来源可以换，门不能换。** 缺省由 `LlmProposer` 生成；也可以手写一份 L1 提案 JSON，用 `rsi propose --from` 登记（存到 `.workspace/rsi/proposals/<id>.json`），再把那个路径交给 `rsi accept --from` 采纳。手写提案**照样跑完整两遍评测与回归门**（没有跳门的 `--yes` 开关），并且 `patch.before` 必须与当前资产正文逐字相等 —— 来源是人还是模型，验证路径是同一条。

## 跨轮自进化

一轮只采纳一条改动（单变量原则），所以「自进化」得靠多轮串起来，而不是靠一轮改三个：

| 能力     | 命令                           | 关键约束                                                                                   |
| -------- | ------------------------------ | ------------------------------------------------------------------------------------------ |
| 连续多轮 | `harness rsi --rounds 5`       | `--max-cost` 是**整次运行**上限（跨轮共享）；没有可采纳改动就停；`--dry-run` 与它互斥      |
| 常驻推进 | `harness rsi --watch`          | 单实例锁 + 心跳；`--every`（缺省 900s）节流；`--max-rounds` / `--until` 停手；信号只停「下一轮」 |
| 跨轮记忆 | 自动                           | 提案前读账本，把 `not_realized` / `reverted` 的方向列进提示词；`historyConsulted` 落盘可查 |
| 回归监测 | `harness rsi regress`          | 拿最近一次采纳的 `candidate` 当基准跑全集；有回归退出码 1                                  |
| 自动回滚 | `harness rsi regress --revert` | 仍过 `revertLast` 的指纹校验（采纳后被人手改过就拒绝）                                      |

### `--watch`：把「写权限留在进程里」落成机制

`--rounds N` 是「跑完就退」，`--watch` 是「一直在，按间隔推进」。多出这一层不是为了省
一次手敲 —— cron 也能定时敲 —— 而是因为**定时器模式下两轮会重叠**：上一轮跑到 7 分钟，
定时器又敲了一次，两个进程同时写 `journal` 与资产。归因失效，而报告看起来完全正常。

所以 `--watch` 提供的是三件定时器给不了的事：

1. **单实例锁**（`.workspace/rsi/worker.lock`，pid + 心跳）。第二个实例启动即失败，而不是
   排队或并行。被 SIGKILL 留下的陈旧锁会**自动回收**（改名留存 `.stale-<ts>`），不需要人
   去删文件 —— 容器里没人会做这一步。
2. **心跳**（每 60s 刷新，10 分钟未刷新判死）。看板 `GET /api/rsi/worker` 因此能回答
   「谁在跑、还活着吗」，而定时器模式下「在跑」和「卡住了」看起来一样。
3. **停手条件先于继续**：预算、到点、无进展、信号，四条都在**开下一轮之前**判；间隔睡醒
   之后**再判一次**（`--until` 很可能正好落在间隔里，不重判就会在到点后再烧一轮）。

信号（SIGINT/SIGTERM）只表示「别开下一轮」：当前这一轮要跑完 —— 资产写入虽然是原子的，
但半轮中断会让这一轮的钱白花。**它不做回滚**，回滚仍是 `rsi regress --revert` 的事。

生产上最省心的组合是 cron / systemd timer 敲一条 `harness rsi --watch`（进程自己常驻），
而**不要**让定时器每次敲一条 `rsi` —— 后者迟早会在某次超时里重叠。

### 中断安全：一次真 SIGKILL 演练（2026-11-28）

单实例锁、原子写、半行修复三条各自有测试，但「组合起来被打断」此前只在纸面上成立。这次
用一个慢端点（每请求 1.5s）把一轮拉到几十秒，在 worker 正跑第 1 轮时 `kill -9`，然后逐项核对：

| 检查 | 结果 |
|---|---|
| 锁文件 | 留在盘上（pid 已死，`currentRound: 1`） |
| 看板判定 | `running:false`，`reason:"pid 19314 已不存在"` —— 心跳还新鲜，是 pid 探测认出来的 |
| 6 个资产文件 sha256 | 全部 `OK`，没有半写 |
| `journal.jsonl` | 1 行、以换行结尾、0 坏行 |
| 临时文件残留 | 无 |
| 重启 | 打印「回收了一个陈旧的 worker 锁」，旧锁改名 `worker.lock.stale-<ts>` 留存 |

两条可以定下来的结论：

1. **资产不可能被写坏**。`atomicWrite` 是「写 `<path>.rsi-tmp` 再 `rename`」，而 rename 在
   POSIX 上原子 —— 任何时刻被杀，目标文件要么是旧的、要么是新的，没有第三种。
2. **唯一可能半截的是 journal 追加**（append 不是原子操作）。所以读侧有半行检测、写侧有
   `journal --repair`。演练里没触发它，是因为这次杀点落在评测/提案阶段 —— 如实记下来，
   别读成「追加永远不会被打断」。

残留的 `.rsi-tmp` 无害（`discoverAssets` 也不收），但会留在盘上。把它当「上次被打断的痕迹」看，比当垃圾清掉更有用。

> 2026-11-28 之后 tmp 名是 `<path>.<pid>.<rand>.tmp`：固定名会让「常驻 worker 与一次
> `rsi accept` 同时写同一个目标」共用同一个临时文件，A 的 rename 可能搬走 B 还没写完
> 的内容。唯一名把这种并发退化成「后写的赢」，而不是「内容串台」。同时补了文件与目录
> 的 `fsync` —— rename 只保证目录项原子，不保证数据块落盘（ext4 延迟分配下，掉电后
> rename 成功而内容全零是真实存在的）。

记忆是软约束：账本里被否掉的方向会以「已经试过、但没成立的方向」出现在提案提示词里，并明确要求换一种改法。**为什么必须这样**：不读历史时提案器每轮都在重置，会把上一轮刚被门否掉的改法原样再提一遍，白烧一遍评测钱 —— 而它看起来完全正常。`historyConsulted` 是三态的：缺席 = 这轮根本没走到提案（基线就超预算 / 没有失败样本），`0` = 提了案但没有可参考的历史，`N` = 带了 N 条历史。

`rsi regress` 默认**只报告不动手**。自动回滚会改资产，而改资产是这套系统里唯一不该无声发生的事，所以要把 `--revert` 显式写出来。

**手工采纳同样可监测**：`rsi accept --from` 也会落一份轮次记录（与自动 RSI 同一个 `writeCycle`），否则 `regress` 只能报「找不到基准」—— 手写提案的改动就永远在监测之外。

**坏记录会让下一轮当场失败**：`.workspace/rsi/cycles/*.json` 或 `journal.jsonl` 里出现半截 JSON 时，读账本与读基准都直接报错（退出码 2），**不会跳过**。静默跳过会让「预测兑现率」与「有没有回归」两个数字同时失去意义；修好记录之前不要继续跑。

## 健壮性加固：七处「以为成立」（2026-11-28）

上一节那次 SIGKILL 演练让「中断之后能继续」这件事有了证据。但演练只覆盖了**一个进程被
杀在一个它控制的时刻**，下面七处是演练照不到的：它们要么需要两个进程，要么需要远端，
要么需要一个「崩在两次写之间」的精确时点。逐条列缺口、旧行为、现在的行为。

| # | 缺口 | 旧行为 | 现在 |
|---|---|---|---|
| 1 | 抢锁不是原子的 | 读 → 判 → 改名 → 写：两进程同时启动都会读到「没有锁」，然后互相覆盖，两个都以为持锁 | `open(path,'wx')` 独占创建；失败才判陈旧、改名让路、重试（最多 5 次） |
| 2 | 锁只保护 `--watch` | 人手跑一次 `rsi` / `accept` / `revert` / `journal --repair` 都不拿锁，与常驻 worker 并发写资产与 journal | 全部写入口共用一把锁（`withRsiLock` / `withRsiLockAsync`），失败文案说清对手是谁 |
| 3 | 采纳有中间态 | 写资产 → 建 lock → 追加 journal 三步之间崩，会留下「资产换了、账本干净」 | 先落**意图**（before/after/待补的条目），崩后按磁盘正文自动补齐或清理（`commit.ts`） |
| 4 | `pending` 清理顺序反了 | 先删备份、再删记录：崩在中间就得到「记录指向不存在的备份」，之后每次启动都失败 | 先删记录、再删备份；只可能留下孤儿备份，超过一天自动清 |
| 5 | 远程调用没有超时 | `fetch` 无 signal，连接挂住会一直等；`--remote` 的 SIGINT 也取消不了 | 默认 15s 超时 + 外部 signal；`GET` 预检对 5xx/网络错误退避重试 2 次，`POST` 重载不重试 |
| 6 | 远程推送可能半新半旧 | 多文件逐个写，中途失败就留下「一部分新、一部分旧」，且不重载 | 先算全部内容再写；失败回滚已写文件并重载，整体报错 |
| 7 | `watch` 单轮抛错即退出 | 一次 429 / 网络抖动就让无人值守的 worker 消失，而只有盯看板的人知道 | 记一次失败、指数退避（1s 起，上限 15 分钟）、连续 3 次才停；`stopReason: 'error'` 且退出码 1 |

另外两件不算「缺口」但同批做的：

- **预算跨进程连续**。`--watch --max-cost` 的累计花费此前只在内存里，被 OOM kill 重启就
  从 0 开始 —— 一个写死 `--max-cost 2` 的 worker，一夜重启五次能花 10 美元，而每一轮的
  单轮花费都合格。现在落在 `workspace/rsi/spend.json`，默认 24 小时滚动窗口
  （`spend-ledger.ts`）。**改上限不等于重置**：从 5 改到 50 不会让已花的 4 美元消失，
  那会是个免费的重置后门。
- **一条自检命令**。`harness rsi doctor` 把散在五个文件里的状态放在一起：锁归属、采纳
  中间态、远程候选残留、journal 可读性、轮次规模、留出集余量、预算窗口。有阻塞项时
  退出码 1 —— 这样才能写「先 doctor 再开跑」的守门脚本。它**不需要模型凭据**：它回答的
  正是「为什么现在起不来」。

三条边界，刻意不做：

1. **不排队等锁**。等锁意味着「两个进程都活着、只是先后写」，而归因失效的代价远高于
   「让人重跑一次」。
2. **不在 `journal` 之前写资产之外的任何东西**。回滚的记录仍然最后写；「资产已回到
   before 但没记账」由 `revertLast` 的指纹分支识别（当前指纹 == `assetsBefore` ⇒ 补记
   一条回滚记录），不去猜第三种情况。
3. **不跨主机探测锁**。同机看 pid、异机只看心跳；跨主机租约是另一个系统的职责。

验证面：604 个测试（新增 `worker-lock` 真子进程并发、`accept-recover`、`pending-order`、
`remote-call`、`watch-resilience`、`spend-ledger`、`rsi-doctor`），门禁
`npm run check` 全绿。

## 真模型跑出来的两个口径问题（2026-11-28）

用 DeepSeek 真端点跑完整闭环时暴露的，mock 下都看不见 —— 假端点的输出长度几乎恒定。

### 一、留出集只有一两条时，token 阈值会否决一切

实测：train 上「修好 1 条、token −14.1%」的提案，在留出集（**1 条**用例）上判成
「通过率没变（100% → 100%）但 token 涨了 194.9%」→ 直接拒绝，这一轮提前结束。

这不是门的 bug（`HOLDOUT_GATE_OPTIONS = {}` 是刻意的：留出集不放宽阈值），
而是**小样本 + 10% 阈值**的固有张力 —— 单条用例的输出长度本来就会因为措辞波动而差一倍。
留给使用者的结论很直接：**留出集至少放 3 条**，否则它更可能误杀提案而不是防过拟合。

### 二、简化轮的「变小」和 gate 的「变便宜」不是一个量

`partitionForShrink` 按**资产字符数**判断提案是否「净简化」，而回归门按**输出 token** 判断。
实测：一个把正文删掉三分之一的提案（过得了简化轮的筛选）让输出 token 涨了 110% ——
因为指令更浓缩、但要求更具体，模型写出来的东西反而更长。

两个维度本身都对（前者是维护成本，后者是运行成本），但**用前者的判据去承诺后者的收益**
会得出反直觉的结论。真要让简化轮兑现「更便宜」，得把筛选条件改成「预测输出 token 下降」，
而那需要先跑一次评测才知道 —— 与「变胖的提案一条都不跑评测」这条省钱纪律直接冲突。
这是一个**已知的、需要权衡的取舍**，不是遗漏。

### 附：评测用例别用 `expect_contains` 卡自由文本

真模型会换词：断言「持久化」时它写「长期存储」，用例就假失败了。
对照用的用例用 `expect_ok: true` + `expect_max_tokens` 才稳；要卡措辞就用 `expect_matches`
写清可接受的正则，别指望模型用你脑子里那个词。

## 成本读数：三本账，各管一段（2026-11-28 真机定位）

一轮 RSI 要跑两遍以上评测，所以在真模型上「闸到底有没有用」是个必须给出确定答案的问题。
答案是：**没有一种读数是全能的**，要分三本账。

| 读数 | 来源 | 精度 | 失效方式 |
| --- | --- | --- | --- |
| 估算 `costUsd` | `pricing` × token | 到 token | 模型没定价 ⇒ 读数不存在；单价填低档价 ⇒ 高峰期低估一半 |
| 余额 `billed` | `GET /user/balance` 差额 | **账户货币最小单位** | 小额花费读出来是 0（实测见下） |
| token | 端点 `usage` | 到 1 | 几乎不会失效，但不是钱 |

### 闸的三种结局，以及第四种

`budget.stopReason()` 只有三个值，但「未定价模型」的处境在 `balance` 之后变了：

- `usd`：下界或估算**已经超过**上限 —— 这一条不看读数可不可信，因为 `spent` 只会偏低，
  偏低都超了就是真的超了；
- `tokens`：token 闸超了；
- `blind`：设了美元上限、**既无可信估算也没有任何余额读数**、又没给 `--max-tokens`。停。
- （旧行为）：未定价时美元闸直接判「没超」然后继续跑 —— 这是**静默失效**，已删除。

有余额读数就不再是 `blind`，因为下界也是读数。但下界**不**让 `costKnown` 变 true：
报告里不会印一个「看起来可信的 0」。

### 为什么余额只能当对账，不能当闸

真机跑出来的数：一轮 `--dry-run`（基线 + 无失败样本），7459 token，账户 ¥2.94。

```text
billed { "currency": "CNY", "amount": 0, "usd": 0, "perUsd": 7.1 }
baseline cost 0 known false
```

那一轮的花费约 $0.002 ≈ ¥0.014 —— **余额只有两位小数，读出来的差值是 0**。
所以余额法有三条硬边界，都必须写在使用者看得见的地方：

1. **精度是账户货币的最小单位**（¥0.01 ≈ $0.0014）。单轮小额花费看不见，累计才看得见；
2. **结算滞后实测约 20 秒**（05:54:00 读到 ¥2.94，05:54:24 读到 ¥2.92 —— 中间那次 `eval`
   花了 $0.0043）。所以**单轮收工那一刻对账，通常读到 0**；跨轮、跨次运行才看得见；
3. 因此它**只上推不下压** `spentUsd`（`Math.max`）：一次「看起来 0 元」的读数绝不能把
   已知花费抹掉 —— 那是「把未知当 0」的变种，只是更难发现，因为报告里有具体数字。

第 2 条还有个直接后果：`--rounds` 下**单轮的 `billed` 会归属错位**（第一轮的钱在第二轮
才入账，于是记在第二轮头上）。**累计总额仍然正确**，单轮金额只是近似 —— 要看总账就看
最后一份记录的 `budget.spentUsd`，或者直接 `harness balance`。

### 那闸靠什么真正生效：**单价填 peak 价**

`examples/starter/harness.config.json` 原先是 off-peak 价（`in 0.15 / out 0.6`），而 DeepSeek 在
UTC 01:00–04:00、06:00–10:00 按 **2 倍**计费 —— 于是闸在高峰时段系统性低估一半，
`--max-cost 0.5` 实际允许花掉 $1。

修法不是「把单价算准」（外部事实，随时段变），而是**让它变成上界**：
示例配置改成 `in 0.3 / out 1.2 / cacheRead 0.147`（peak 价与 peak 下的缓存乘数）。
代价是 off-peak 时段会提前一点停，收益是**任何时段都不会超支**。

一句话的口径：**估算管上界，余额管对账，token 管兜底。**

### 用法

```bash
harness balance                 # 现在还剩多少钱（原币 + 折算 + 是否可调用）
harness balance --json
harness rsi --max-cost 5        # 未定价模型上：按余额下界对账，不再是「基线跑完就停」
harness rsi --max-cost 5 --max-tokens 200000   # 两个都要：钱对账 + token 兜底
```

配置（全部可选）：

```json
"balance": { "url": "https://api.deepseek.com/user/balance", "perUsd": 7.1, "warnBelowUsd": 0.5 }
```

- `url` 省略时按 `endpoint.baseURL` 推导（`api.deepseek.com` 自动识别）；
- `perUsd` 是非美元账户的折算率，缺省 `7.1`（内置快照值；报告里同时留**原币金额**，
  审计看那个）；
- `warnBelowUsd` 给了就在开跑前检查一次余额并告警 —— 这是**与单价无关**的唯一硬事实；
- `"balance": false` 关掉（关掉之后未定价 + 只设 `--max-cost` 又会回到开跑前拒绝）。

## `rsi --remote`：为什么它要「先写盘」

RSI 的一轮是「改资产 → 用改过的资产重跑 → 比较」。本地这条路里补丁只活在内存
（`applyPatch` → `runSuite({ assets: patched })`）；远程必须把候选**写到服务读的那个文件**
才可能被看见。于是顺序反过来成了「先写盘 → 再验证」，而这是整条路上唯一能捅出事的改动。

### 配置

```json
{
  "remote": {
    "url": "http://127.0.0.1:18090",
    "tokenEnv": "RSI_ADMIN_TOKEN",
    "agent": "report",
    "allowStaging": true,
    "prompts": { "agent:report": "../agentia-service/prompts/report.md" }
  }
}
```

- `prompts` 是**唯一必须显式写出**的东西：`agent:<id>` → 服务读的那个文件。猜目录结构
  的后果是「每轮提案都被判没改善」，而那个症状看起来像模型不行。
- 只收 `agent:` 前缀：service 侧目前只把 agent 的系统提示词外置了。
- `allowStaging` 默认 **false**。远程只有一份活的提示词，验证期间服务对外提供的就是
  候选 —— 这个暴露面是机制固有的。打开它等于签字确认「这是一台评测/预发机」。

### 一轮里的顺序（顺序本身就是安全性）

```
回收旧 pending  →  allowStaging  →  预检本地/远端 digest 一致
   →  proposer  →  stage(写盘 + reload)  →  跑远程评测  →  restore(写回 + reload)  →  门
```

四条容易被忽略的：

1. **回收排在最前面**，哪怕 `allowStaging` 已经关掉：上一轮崩在「写盘之后」时，盘上留着
   一个没被验证过的提示词，还原是安全动作，不该被开关挡住。
2. **预检不一致就拒绝开跑**，除非显式 `--sync-remote`。不一致意味着基线不是当前资产跑
   出来的，于是「通过率涨了」可能只是远端本来就不一样。实测报错长这样：

   ```
   agent:report: 本地 a1743d33afbd / 远端 4c8dfb0f0857
   ```

3. **restore 之后必须 reload**。只把文件写回去而不重载，服务仍跑着未验证的候选 ——
   这是最隐蔽的一种「以为还原了」。
4. **采纳之后要 push**。verify/holdout 各自跑完都会撤台，所以门通过时远端已经回到旧版；
   不再推一次的话，本地资产是新的、服务还是旧的，下一轮预检立刻报漂移。

### 崩溃安全：`pending` 记录

写盘前把原内容备份到 `.workspace/rsi/pending/`，再原子写一条
`.workspace/rsi/pending.json`（提案 id / 目标 / 文件 / 备份路径）。崩在这之后，
下一次 `rsi` 会：还原文件 → 重载 → 删记录，并打印

```
回收了一个未完成验证的远程改动：agent:report（提案 p-1795839739254-0）已还原并重载
```

三条口径：

- 还原是**幂等**的（写回备份 + 重载），所以「已还原但没来得及删记录」再跑一次也无害；
- 还原时重载失败 ⇒ **保留记录**并报错（远端可能还跑着候选，清掉记录等于假装没事）；
- 备份丢了 ⇒ `rsi.bad_record` 直接停手，不猜。

### 踩过的坑：基线差点跑在本地

远程模式刚接上时，`runCycle` 里**只有候选**用了注入的 `runner`，基线那句 `runSuite` 漏了它。
症状极隐蔽：报告里 `model` 字段各自报各自的、通过率看着也合理，实际是「本地模型跑基线、
远程服务跑候选」，两套口径被放进同一个回归门。

暴露它的是一条更细的线索：失败模式显示「偏向改（无资产命中）」——因为本地那次根本没有
派单，`subagents` 是空的，归因拿不到「该改哪个资产」。修好之后同一轮变成
「偏向改 agent:report」，token 差也从 **+411%** 回到 **−4.9%**（前者是两套计费口径相减
的产物）。

教训写在这里：**远程模式下凡是跑评测的地方都要同一个 runner** —— 基线、候选、留出集、
回归检查四处，漏一处就变成「测了两个东西」。`tests/cycle-runner.test.ts` 用「runner 被
调用过」钉住基线这一处（不钉数字：这个 bug 的症状不是算错，是测了另一个对象）。

### 真机验证（2026-11-28，本机起真 agentia-service + DeepSeek）

基线修好之后重跑的干净一轮：

| 步骤 | 结果 |
|---|---|
| 基线 | `risk` 用例 0/1（要求回答含「反例」，提示词没这条） |
| 归因 | 「偏向改 agent:report」（意图层派单 ⇒ 远程 runner 报 `subagents`） |
| 候选 | PASS：通过率 **+100pt**、token **−4.9%** |
| 采纳 | `agent:report` 落盘；本地与远端 `diff` 一致、`pending` 清空 |
| 服务行为 | 新请求仍按新提示词回答（前两行「结论：」「置信度：」） |

`--watch` 与 `regress` 也各跑了一条真机：

| 检查 | 结果 |
|---|---|
| `rsi --watch --remote --max-rounds 1` | 「worker 启动」→ 1 轮采纳 1 条 → 「跑满上限轮数」；锁释放、pending 清空 |
| watch 之后本地/远端 | `diff` 一致；服务回答里真的出现了新加的「置信度：」 |
| `rsi regress --remote` | 「采纳时通过 1 条，现在通过 1 条 · 没有回归」 |
| 把服务停掉再跑 regress | `连不上 .../admin/prompts` ⇒ 证明它确实走远端，没有偷偷退回本地 |

`regress` 是**只读**的，所以它不受 `allowStaging` 约束（那道门是给「写」签字的）。

过程中修掉一个真 bug：`POST /admin/reload` 带 `content-type: application/json` 却没有 body
时，Fastify 直接 400（"Body cannot be empty…"）—— 于是所有 stage 都在重载这一步失败。

### 留出集在远程模式下：能跑，但继承了小样本问题

真机跑了一轮带 `split: holdout` 的远程验证：train 修好 1 条（+100pt）之后，留出集
**确实被 stage 上去跑了一遍**（stage → 远端评测 → 撤台，`pending` 清空、远端文件回到原样），
然后按门拒绝：

```
留出集第 1 批 1 条
  拒绝 p-…：留出集未通过：通过率没变（100.0%）但 token 涨了 140.3%（阈值 10%；成本不可比，按 token 判）
```

这正是本地早就记过的那个坑（[留出集只有一两条时，token 阈值会否决一切](#一留出集只有一两条时token-阈值会否决一切)），
在远程模式下原样复现 —— 不是远程特有的问题。**结论不变：留出集至少放 3 条。**

### 不合并 stage：先量了，收益是 0.6 毫秒

verify 与 holdout 各 stage 一次，所以一个提案最多两次「写盘 → 重载 → 跑 → 撤台」。
看起来该合并，先量了一下代价（本机真服务，连打 10 次重载）：

| 指标 | 值 |
|---|---|
| `/admin/reload` 耗时 | 中位 **0.6ms**、最差 14.5ms |
| 重载期间 `/healthz` | 未被阻塞（并发探测零失败，最大 9.3ms） |

合并能省的是 ~1.2ms 与一个**毫秒级**的撤台窗口；要付的代价是把 `loop.ts` 里最绕的一段
（赢家选定 → 预算检查 → 留出集批次 → 消耗账）重排。不值得 —— 这一条记在这里是为了让
下一个人不必再量一遍。

### 还没做

- **多 agent 目标**：一次提案只改一个资产（单变量原则），所以每次只动一个文件；但如果
  服务侧有多个 agent 都外置了提示词，映射要一条条配，没有「整目录同步」这回事。

### 路由判据在真远程数据上的验证（判据 27）

`isWorthAccepting` 里那条「通过率涨了但路由塌缩也不采纳」此前只有单测覆盖。
2026-11-28 用 NAS 上真模型服务的两份报告验了：同一套用例跑两次，**只改 frontmatter
的 `route:`**，其余不动。

| | 通过 | 路由准确率 | token |
|---|---|---|---|
| A（声明 `report`，服务真派 report） | 1/2 | **100%** | 8795 |
| B（声明 `billing`，服务仍派 report） | 1/2 | **0%** | 8364 |

`gate(A, B)` 自己判 **ok=true**（通过率持平、token 还降了 4.9%）—— 也就是说
**单靠回归门会放行**；`isWorthAccepting` 因为 `routeAccuracy` 掉了而拒绝。
这条判据不是冗余的：通过率看不见「所有请求都被派给同一个 agent」这种塌缩。


## L2（代码补丁）的评测门：`patch --eval`

L2 之前是**独立通道**：`harness patch x.diff` 只跑配置里的验证命令（通常是 `npm test`），
于是「这个代码补丁值得采纳吗」与 harness 的评测集毫无关系。单测保证「没弄坏代码」，
评测保证「agent 在真实用例上没变差」—— 这两件事不能互相代表。

`--eval` 把评测集接成验证门：

```bash
harness patch fix.diff --eval            # 只验证
harness patch fix.diff --eval --yes      # 验证通过后落盘（仍需人工签字）
```

三条设计取舍：

1. **跑的是「当前这份 harness」，不是沙箱里那份**。沙箱是被打补丁的仓库，它不一定有
   `src/cli.ts`（业务工程就没有）。用被打补丁的代码去验证被打补丁的代码，结论没有意义。
   所以入口取 `import.meta.url` 的绝对路径；**源码优先、`dist/cli.js` 兜底** ——
   反过来会让「改完源码再验证」验到一份过期的构建产物（这个坑踩过三次）。
2. **报告写到沙箱外**。沙箱验证结束会整体删除，写里面等于没写。摘要（total/passed/
   passRate/tokens/cost）从文件读回来，进 journal 的 `code.verify.eval`：
   `rsi status` 于是能显示 `评测门通过（1/1，100.0%，$0.0001，145ms）`。
3. **不放宽 `--yes`**。L2 与 L1 的最大区别：改提示词坏了大不了回滚，改代码能弄坏构建。
   RSI 不该有「自己决定改代码」的权力 —— 提案仍由人或外部 agent 交进来。

真机验证（2026-11-28，假 Anthropic 端点，零成本）：

| 场景 | 结果 |
|---|---|
| 评测全绿 | `验证：PASS`，`评测：1/1（100.0%），13 token，0.0001 USD`，`--yes` 后 journal 带 `eval` 摘要 |
| `expect_contains` 改成不可能满足 | `验证：BLOCK`，退出码 **1**，尾部打 `有 1 条用例没过 —— 代码补丁不许降低通过率` |
| 落盘后 `patch --revert` | 文件被删回，`rsi status` 里多一条 `rejected`（回滚不改原采纳行） |
| L1/L2 同账本 | `rsi status` 同时列出 `code:helper.ts` 与资产采纳 —— 这才是「同一闭环」 |

一条诚实的限制：沙箱的 root 是沙箱目录，`loadEnvFile` 找不到主仓的 `.env` ——
凭据必须在**真实环境变量**里，否则评测会在沙箱里报「缺少凭据」。
